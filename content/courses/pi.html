终端入口与串行等待

输入界面的循环等待 session.prompt 完成，异常交回 showError。可见的 Enter 并没有直接触发 Provider；这解释了为何界面收到输入而模型没有请求，仍可能是前置失败。 先画两条线：普通新请求进入 prompt；已有运行的新输入进入 steer/follow-up。不要因为界面允许继续打字就推断 Agent 支持两个主运行并发修改同一状态。排查时保存输入类型、是否正在流式运行和具体错误阶段。

预处理顺序的行为含义

扩展命令先有机会处理输入，然后检查压缩状态，输入钩子可能改写或消耗消息，之后才展开Skill与模板。这是一条会改变语义的有序链。 例如钩子把一条命令改成另一条，模板展开读取的就是新内容；若提前展开，行为可能不同。分析时同时保留原始输入与最终模型消息，避免把扩展生成文字当作用户原话。自定义处理已经完成也可能不需要模型请求。

请求拒绝与排队的区别

await表示当前交互路径在等待，但运行是否允许新输入还受Agent状态和Session预处理约束。输入被拒绝、排队、改写和执行是四种不同结果。 消息队列改变的是下一次何时进入循环，不自动给予越过压缩门禁或认证检查的权限。读源码时从prompt向上追调用者，再向下追Agent.prompt的运行保护，防止把UI线程的响应性与Agent状态并发安全混为一谈。

# Pi Agent Harness

This is the home of the Pi agent harness project including our self extensible coding agent.

* **[@earendil-works/pi-coding-agent](packages/coding-agent)**: Interactive coding agent CLI
* **[@earendil-works/pi-agent-core](packages/agent)**: Agent runtime with tool calling and state management
* **[@earendil-works/pi-ai](packages/ai)**: Unified multi-provider LLM API (OpenAI, Anthropic, Google, …)
同一运行时的多种入口

默认交互模式创建InteractiveMode；CLI其他模式是对同一运行时的不同呈现。不能把终端、RPC或打印模式当成三个独立的大脑。 要复用执行语义，应保持输入归一化和事件消费契约，再更换宿主入口。不同入口可能有不同取消、流显示与错误反馈，必须分别测试；一个CLI成功不自动证明另一个传输模式无误。

模型与工具的闭环

 * Fail all tool calls from an assistant message that was truncated by the
 * output token limit. Streamed tool-call arguments are finalized with a
 * best-effort JSON salvage parser, so a truncated message can yield tool calls
 * whose arguments parse and validate but are silently incomplete. None of them
 * are safe to execute; report each as an error so the model can re-issue them.
 */
async function failToolCallsFromTruncatedMessage(
	toolCalls: AgentToolCall[],
	emit: AgentEventSink,
): Promise<ExecutedToolCallBatch> {
	const messages: ToolResultMessage[] = [];
	for (const toolCall of toolCalls) {
		await emit({
			type: "tool_execution_start",
			toolCallId: toolCall.id,
			toolName: toolCall.name,
			args: toolCall.arguments,
		});
		const finalized: FinalizedToolCallOutcome = {
			toolCall,
			result: createErrorToolResult(
				`Tool call "${toolCall.name}" was not executed: the response hit the output token limit, so its arguments may be truncated. Re-issue the tool call with complete arguments.`,
			),
			isError: true,
		};
		await emitToolExecutionEnd(finalized, emit);
		const toolResultMessage = createToolResultMessage(finalized);
		await emitToolResultMessage(toolResultMessage, emit);
		messages.push(toolResultMessage);
	}
	return { messages, terminate: false };

Module 4 · Trust boundaries

拿到工具箱，不等于装上门禁

这一节区分四件常被混为一谈的事：模型看见哪些工具、项目资源是否加载、工具调用能否被策略拦截，以及进程最终拥有的操作系统权限。

工具箱与门禁比喻：工具清单像“工人会用什么设备”；Project Trust 像“是否让本项目带来的插件进场”；沙箱才像“围墙和门禁”。

Capability 与许可策略必须分开审查。

Default loadout

默认 Agent 一开始就有四种高影响能力

read

读取文件内容，可能接触敏感本地信息。

bash

启动 shell 命令，影响范围由进程与操作系统决定。

edit

对已有文件做精确修改。

write

创建或覆盖文件内容。

Project trust

Trust 控制项目带来的代码和设置是否被加载

Project Trust 解决“是否执行项目带来的代码”，不是“bash 能否访问某个目录”。

Operating-system boundary

上游明确写着：Pi 默认继承启动它的进程权限

Module 5 · Session state

会话是账本，不是一块会被擦掉的白板

这一节说明消息何时落盘、为什么每条记录都有父节点、`/tree` 如何保留旧分支，以及压缩为什么只改变“模型下一次看什么”，不等于删除完整历史。

账本与书签比喻：JSONL 是只往后写的账本；parentId 是页间引用；leaf 是当前书签；分支只是移动书签后继续写新页。

JSONL 让一段会话可以作为可检查的事件序列保存。

Persistence trigger

只有完成的消息事件才进入常规消息账本

流式的 message_update 用来刷新界面，但这里没有逐 token 写成一堆永久消息；最终完成事件才形成常规会话记录。

Append-only tree

每一条新记录都成为当前 leaf 的孩子

Branching

回到旧节点不会覆写后来发生的事

root ─ user A ─ assistant A
                   ├─ user B ─ assistant B   ← 原路径仍在
                   └─ user C ─ assistant C   ← 当前 leaf

leaf 是模型上下文路径的书签，不是“文件最后一行”的同义词。

Compaction

压缩替换模型视野，不抹掉账本

Module 6 · Safe change map

先选插座，再追熔断点

最后一节把前五节变成行动地图：何时用 Prompt、Skill 或 Extension，何时才改核心；发生故障时，如何按 preflight、Provider、tool、session 四段收集证据。

配电盘比喻：Extension API 是预留插座；事件是电路测试点；错误与 stop reason 是熔断器标签。先接对插座，故障才不会蔓延到整台机器。

Extension 比复制一份核心代码更容易升级与隔离责任。

Public seams

扩展可以观察生命周期，也能新增工具和命令

Choose the smallest seam

Prompt、Skill、Extension 与核心改动解决不同问题

Prompt Template

复用一段用户请求格式；不新增执行能力。

Skill

按需给模型一套工作方法与资源说明；仍由现有工具执行。

Extension

新增可执行工具、事件策略、命令或界面。

Core change

只有公共生命周期或不变量本身要变时才触碰。

Failure ladder

先找停止阶段，再讨论根因

Steer and verify

把需求写成“责任层 + 不变量 + 证据”

表象

用户看到什么？是无响应、报错、工具失败、历史丢失还是权限越界？

责任层

TUI、AgentSession、Agent Core、Provider、Tool 或 Session，哪个最先违背预期？

不变量

例如“截断参数绝不执行”“旧分支不被修改”“未 trust 不加载项目扩展”。

证据
