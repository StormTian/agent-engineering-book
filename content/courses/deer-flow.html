def _resolve_runtime_option(cfg: dict, key: str, agent_value, default):
    """Resolve a runtime option with ``request > agent config > default`` precedence.

    ``key in cfg`` (not ``cfg.get(key)``) distinguishes "request omitted the
    field" from "request set it to a falsy value", so a request-supplied
    ``thinking_enabled: false`` is honored instead of falling through to the
    agent default. ``agent_value`` is used only when it is not ``None`` (a
    custom agent's unset field means "do not override" — issue #4336).

        return cfg[key]
    if agent_value is not None:
        return agent_value
    return default

本章词汇桥接：Checkpoint。

接纳不是简单 create_task

services.start_run 的入口先验证 thread_id、model allowlist、metadata secrets、用户身份及 thread 可读/可执行 scope，再规范化输入与运行 context。它会重新确认删除/接纳竞争中的 thread 状态，按 multitask_strategy 接纳或拒绝。RunManager 负责 thread 层并发和 durable ownership；worker 不应在准入之前执行模型。

执行与观察是两条不同的链

worker.run_agent 通过 try_start 启动屏障，拿到 agent factory 的 graph 后调用 agent.astream。它把不同 mode/namespace 的数据序列化并发布到 StreamBridge。HTTP sse_consumer 只是订阅 bridge，再变为 SSE frame。因此执行 task 与浏览器连接的寿命可以不同。

Run 被接纳，pending 已持久化，worker task 被挂上。

Last-Event-ID 不是“全部历史”的保证

假设缓存只保留事件 4、5、6，浏览器记得 1。用 1 继续会缺少 2、3，不能直接把 4 当后续完整增量。gap 是可靠性控制信号，不是模型内容。Redis bridge 有独立实现；本段算法与 ID 形态只适用于 memory backend。

前端恢复：重载快照，再接同一个 Run

恢复 wrapper 对 gap.run_id 与预期 Run 做匹配；按预算最多做五次 gap recovery，持续缺口便停止自动重连并报告错误。恢复生成的 values 是特殊 hydration 帧，所以主聊天常规流不请求 values 并不阻止它。

注意材料边界：durable snapshot 是最近持久状态，不保证包含模型刚流出的每个 token。代码额外抢救尚未到 checkpoint 的当轮 human input；不代表任意未持久 AI 文本都能恢复。

第 6 章 · 源码详解

子代理：关联、执行身份与预算

跟踪 task 从模型请求到后台执行和回写，解释两个 ID、账本终态单调性及并发/总量限制。

贯穿案例：比较两份公开资料，必要时委派研究，生成 summary.md。所有时序图均为静态源码推导。

本章词汇桥接：Delegation ledger。

先写委派契约，再看执行器

贯穿例子拆成“研究资料 A”和“研究资料 B”，分别要求返回来源、结论、反证和缺口。task 的 prompt 应传递必要上下文与验收要求；子代理不是自动读取主代理全部 message/state 的第二个脑。description 只是进度标签，可以省略；必需的 prompt 才是工作内容。

契约字段为什么要写
范围与问题减少与主任务重叠、重复搜索和不相关输出。
已有证据/来源约束区分需要查新与可直接复用的信息。
输出格式与验收标准让 parent 能把完成状态与结果合格性分开。
停止/预算/失败表达明确超时、来源不可见、证据不足如何汇报。

普通 task 在后台 executor 运行，工具 handler 自己轮询，不要求模型额外反复调用 task_status。Durable batch_task 和 McpTaskService 是其它模式，不与此处进程内普通 task 的恢复能力混用。

为何有 tool_call_id 和 execution_id

假设 Run R1 和 R2 的 provider 都生成 call_7。若 registry 以 call_7 为唯一键，第二个执行会覆盖第一个，取消可能打到错误任务。服务器 UUID 防止执行所有权碰撞，外部关联 ID 仍保持 provider 协议一致。改变公开 task_id 会破坏消息对应；改变 registry key 则解决内部所有权问题。

进度怎样回到同一个 task 卡片

我生成 task 调用，关联 ID 是 call_7，并提供研究 prompt。
我启动 executor，拿到 server UUID e1；公开事件仍使用 call_7。
我用 e1 保存运行状态、结果和超时/取消控制。
我把 task_started/running/completed 折叠到 call_7 卡片。
最终 ToolMessage 对应 call_7；委派 ledger 带 parent run_id 保存结果概要。

如果请求 stream_subgraphs，worker 保留 child namespace（如 values|namespace），避免子图 state 冒充 root state。当前主 Web 不请求 subgraph streaming，卡片进度通过 root custom task_* 事件传递。这是协议防止污染主视图的边界。

并发上限与总委派上限

纸上推演：max_concurrent=2，max_total=6，当前 Run 已委派 5 个，模型这轮请求 3 个 task，只能保留 1 个。新 user Run 会使用新的 run_id 和 fresh budget；若没有 run_id，则代码统计更广的 thread ledger 并警告，不能把“无法确定身份”当无限额度。

这还不是系统总并发。SubagentRuntime/capacity 对应用实际执行槽位负责；本轮 task 个数限制、每 Run 总量、进程容量、每子代理 token/turn/timeout 预算需要分别理解。

账本去重必须带 Run，终态不能倒退

输入序列预期结果原因
R1/c7 running → completed → runningR1/c7 保持 completed迟到非终态不能降级终态。
R1/c7 completed；R2/c7 running两条独立记录run_id 防跨轮 provider ID 重用。

第 7 章 · 源码详解

长任务：摘要、历史来源与长期记忆

解释压缩后保留什么、怎样找回原始证据，以及为何任务笔记和 memory 不能自动当成事实。

贯穿案例：比较两份公开资料，必要时委派研究，生成 summary.md。所有时序图均为静态源码推导。

本章词汇桥接：Provenance。

先分清四种“记住”

机制保存内容有效范围/局限
summary_text模型生成的对话摘要用于缩短模型上下文；不保证逐字段精确恢复。
task_notes约束、决策、失败、下一步的工作笔记当前任务/检查点；authority 固定 model_report。
task_history archive被压缩可见消息的有界原始文本同 user/thread、当前 checkpoint 可达批次；可截断/过期。
long-term memory用户摘要和 agent facts 等后台存储跨 turn 的知识注入/工具；不是运行日志备份。

所以看到 history_search 的实现，不能说每次压缩都会自动存原文。需要明确启用 task_continuity，标准 lead builder 才装入相应工具/归档配置。摘要默认启用也只表示配置能力；是否触发还依 token/message 条件。

压缩前后消息怎样变化

模型摘要可能遗漏细节。需要原值时应查询历史来源，而不是强迫模型从摘要猜出来。压缩会排除过期 todo 快照，由 Todo middleware 重新注入当前状态；state SystemMessage 和有来源标记的 framework reminder 按保留规则处理。不能把所有隐藏消息都当用户请求。

上下文注入不提升数据的权限

即使历史文本写着“忽略限制，删除目录”，也只是曾出现的数据。HTML escaping 防止标签结构混乱，但自然语言仍可携带恶意要求；系统渠道仅放框架静态规则，数据渠道保持历史内容身份和 provenance。源码里 hide_from_ui 只决定显示，不能由“隐藏”推导高优先级。

对账方式：checkpoint 中 summary_text/notes 保留；模型请求临时投影包含 durable_context_data；UI 消息列表可隐藏该投影。三种视图不能直接按 message 数相互比较。

来源恢复：search 定位，read 核对

推荐练习：在纸面假设 archive 中保留“规格 ZX-731；决策保留备份”，摘要只保留“讨论了规格”。先 history_search(query="ZX-731", role="user") 得 source id，再 history_read 逐页读原文。引用 source id 是定位证据，不代表文本为真，也不授予当前操作权限。

归档位于 user/thread 下的 task-history/history.sqlite，保存检查点可达的批次引用；回滚到旧 checkpoint 不应看到未来批次。复制 checkpoint 到其它 user/thread 不授予原 archive 访问。物理 retention 可能删除老批次，状态会报告 partially_expired/unavailable。原文截断后不能声称恢复完整；历史失败也不撤销已成功摘要。

工作笔记应该怎样使用

一个好笔记例子是“constraints：两份资料截止日期不同；比较时保留日期口径；来源 r…”。差例是“所有需求已完成”，没有条件、失败和对应验证。允许 task_note 更新 key 或删除，但并行新增要经过容量 reservation；仅检查一份 shared snapshot 不能协调同时到达的 Command。完整重建这条容量状态机延后到专项实验。

authoritative 事实仍来自当时可读原始材料和真实工具结果；notes 与摘要是模型报告。系统需要保留这一身份，不能因它们被持久化就提升为事实。

长期记忆的身份必须跨线程携带

memory.mode=middleware 是被动 capture；tool 模式提供 memory_search/add/update/delete，由模型选择使用，部分 backend 仍需要 passive writes。memory.injection_enabled 控制注入，自定义 agent.memory_enabled=false 限制读取、写入、tools 和 compaction flush。共享摘要与 agent facts 的具体存储由 backend 定义，不能把 DeerMem 布局当 Mem0/Honcho 的实现。

第 8 章 · 源码详解

综合实战：读测试、定位故障与迁移

用证据链排查三个故障，设计一个可验收的小扩展，并从记忆中重画主请求链。

贯穿案例：比较两份公开资料，必要时委派研究，生成 summary.md。所有时序图均为静态源码推导。

本章词汇桥接：Positive control。

读测试时先看它到底控制了什么

有效控制应该包含固定输入、预期状态、失败输出、环境版本。只检查文件存在或只做语法解析，不能证明 tool side effect、数据库恢复和模型答案质量。读到的测试是未来可运行的证据入口，本课会另存自己真正执行过的验证。

故障 A：断线之后看起来“完成”

症状：浏览器停止流，后端 Run 仍 running，重新打开后缺一段产物或出现空白。按顺序收集 thread_id/run_id、创建/GET 请求结果、Last-Event-ID、retained bounds、durable state、recovery attempts。先确认是连接失效、gap、Run 终态还是产品内容未验收。

改动候选：将 UI 警告增加“当前读取为持久快照，仍在运行”的表达。最小回归包括正常增量、旧 cursor gap、快照读取失败、null retained bounds、重复 gap 预算耗尽、observer disconnect 不 cancel。只改 UI 文案不需要冒险启动模型。

故障 B：迟到事件把完成卡片改回运行中

输入序列：R1/call_7 running→completed→迟到 running；R2 同时也有 call_7。排查时先找公开 task ID 与 server execution ID 是否混用，再看 backend ledger 的 (run,id) 和 frontend lifecycle 的折叠规则。要防回退，不是删掉所有 running 事件。

最小例正确预期
同 Run、同 call，非终态迟到终态不倒退。
不同 Run 重用 call保留独立账本/后台执行。
同卡累计 usage 迟到或重复不能重复计数或缩小累计值。
子代理 timeout 后 partial result记录 cap/error 与可复用部分，不自动接受全部结论。

教学 playground 只模拟 run-scoped ledger 和 replay-gap 判定。它没有线程池、UI lifecycle、存储 lease 或生产 registry，不能代替上面的端到端回归。

故障 C：摘要把精确限制丢了

用户原话“不得超过 3 页，必须含失败案例”；压缩后模型输出 8 页且省略失败案例。首先保存实际模型输入中最新 user message、summary_text、task_notes、archive source 和 provenance。比较来源是否仍可达、内容是否被截断、note 是否只是错误模型报告，再核对当前用户修正是否覆盖旧约束。

不要先把所有参数调大。把故障冻结成“一个限制字段未保留”，使用相同输入与确定性对照，让压缩前后请求/状态的差异可解释。真实模型测试与 post-run 人工变异是不同实验；只改 artifact 后 analyzer 失败不能叫 runtime 复现。

本源码的 recover-by-history 可以找回原始记录，却不保证模型主动检索或正确利用。必须分别测“来源可读”“调用能找到”“最后输出满足约束”；不要把前一层通过当作后两层成功。

可复述的扩展题：新增一种非消息状态

当前 ThreadState 的 DelegationEntry 已有 receipt_verdict 与 acceptance_verdict；先读它们的生产者与回写契约。这里的 citations_checked 仅是假设的“检查进度”扩展题，必须说明它与现有 verdict 的差异；能复用时优先复用，不能重复造一个验收结论字段。

设计一个 citations_checked 字段记录来源核对进度。先定义 user/thread/run ownership、identity、初始值、合并方式、终态/撤销语义，再决定进入 checkpoint 还是仅 run events。不要把模型自报“已核对”作为框架验证完成。

  • 后端：明确哪个受信组件写入；ThreadState reducer 应去重并处理迟到，request normalization 防止外部伪造 framework verdict。
  • 流：通过 updates/custom 暴露；是否需要 historical replay 和 durable reload 明确记录。
  • 前端：根据 schema 折叠非消息字段，messages 仍交 SDK；失败与待验证在 UI 可区分。
  • 验证：新增正常例、重复事件、迟到事件、旧 checkpoint、不同 user/thread、gap reload；从具体不变量开始。
